* Executive summary

This document is a combined *compliance gap analysis* against the
~rust-template~ that ezpz-dndz was scaffolded from, plus an
*optimization / refactor plan* with a forward-looking *data model*
covering the features we've built, the ones in flight (compendium),
and the ones we know are coming (auth, encounter persistence, UI
preferences, CR calculator, etc.).

The big findings, in priority order:

1. *~Main.elm~ is 5,849 lines.* Single-file frontend; everything from
   ~Model~ through every modal view lives there.  Splitting along
   feature boundaries is the highest-leverage refactor.
2. *~Encounter.elm~ is 1,545 lines* and growing.  Each subsystem
   (death saves, conditions, save notices, timers, roster mutators,
   lifecycle hooks) has earned its own module.
3. *Modal chrome and modal-state plumbing are duplicated 6–7 times.*
   Extract a single ~viewModal~ helper plus a generic
   ~withMaybe : (a -> a) -> Maybe a -> Maybe a~ helper to collapse
   six near-identical ~with*Ui~ functions into one.
4. *~crates/server/src/dice.rs~ violates the template's "semantic
   thiserror" rule* — it returns bare ~std::io::Result<_>~ from its
   public API.  Refactor to a ~DiceHistoryError~ enum.
5. *Dice routes don't participate in the OpenAPI schema.*  The
   ~web_base.rs~ ~ApiRouter~ generates a spec for ~/healthz~,
   ~/me~, etc., but ~dice.rs~ uses the plain axum ~Router~ and is
   invisible to ~/api-docs/openapi.json~ + ~/scalar~.  Same fix
   when we land the compendium routes — use ~ApiRouter~ from the
   start.
6. *No automated tests anywhere.*  Template contract is "tests must
   exit with proper error codes."  We need at least: ~elm-test~ on
   the four pure Elm domain modules and integration tests on the
   server crate's mutation routes.
7. *Documented future features have no data model on paper.*  The
   refactor needs to land with a model that already accommodates
   users, sessions, preferences, encounter persistence, and CR
   calculation, even if the schema isn't exercised in v1.

The visual data model (rendered to ~docs/diagrams/data-model.svg~
via d2) anchors the future-state in one picture.  Everything in
this plan is shaped to land us there incrementally without
rewrites.

** Why d2 (over Mermaid / PlantUML / Graphviz)

- *Single statically-linked binary*, packaged in nixpkgs.  No
  Java, no headless Chrome, no node.
- *Text source*, so diffs are reviewable in PRs.
- *SVG output* renders crisply at any zoom; embeds cleanly in
  ~README.org~ and ~docs/ARCHITECTURE.md~.
- *ELK layout engine* (built in) handles entity-relationship
  graphs without manual layout tweaking.
- Project already has ~prettier~ for CSS / Markdown; d2 adds
  diagram rendering with a comparable "edit a text file, see the
  output" workflow.

If we later need sequence / flowchart diagrams inline in
~.org~ files, ~mermaid~ source can be embedded directly in
~#+begin_src mermaid~ blocks; many org-mode renderers handle
those natively without a separate tool.  d2 is the durable
"static artifact" path.

** Key modeling decisions

- *Encounters store full state as ~jsonb~* rather than normalizing
  combatants into a relational table on day one.  Rationale: the
  encounter is a *write-mostly* document; combat happens fast and
  every Next Turn click would touch a dozen joined tables.  We
  also already have a JSON-encodable Elm record.  The
  ~combatant~ table exists for queries the snapshot can't
  answer cheaply (e.g. "show me everyone Lyra has fought").
- *Snapshots* (~encounter_snapshot~) capture full state for undo
  + crash recovery.  Cheap because we never re-parse them; we
  just deserialize the most recent on demand.
- *Bundled vs. user-owned* compendium creatures share a table;
  ~owner_id IS NULL~ means bundled.  ~visibility~ further
  distinguishes private / shared / official among user-owned.
- *Provenance preserved but decoupled*: a ~combatant~ keeps its
  ~creature_id~ back-reference for "Quick View" but stores its
  full stat block in ~instance_data~ so a deleted compendium
  creature doesn't break a saved encounter.
- *Roll → encounter linkage* via ~dice_roll.encounter_id~ enables
  a future "this round's rolls" filter in the dice modal without
  changing the wire format.

* Compliance gap analysis

The template's distinctive constraints, with our current state
audited against each:

** Workspace + crate boundaries — *PASS*

Three crates (~cli~, ~server~, ~lib~) match the template's
shape.  ~main.rs~ in both binaries acts as a pure orchestrator;
sibling modules handle config, logging, etc.  The naming
(~ezpz-dndz-cli~, ~ezpz-dndz-server~, ~ezpz-dndz-lib~) follows
the convention.

** Semantic errors via thiserror — *PARTIAL FAIL*

Compliant: ~web_base.rs~, ~config.rs~, ~auth.rs~ (skimmed),
~main.rs~ all use thiserror with descriptive variant names.

*Gap*: ~crates/server/src/dice.rs~ exposes ~std::io::Result<_>~
and ~std::io::Error~ on its public API
([dice.rs:78](crates/server/src/dice.rs#L78),
[dice.rs:88](crates/server/src/dice.rs#L88),
[dice.rs:102](crates/server/src/dice.rs#L102),
[dice.rs:125](crates/server/src/dice.rs#L125)).  This violates
the rule from ~CLAUDE.md~ / ~llms.org~: "Do not just wrap or
propagate a FileMissingError or FileWriteError. … Include
something either about the error itself … or about the process
in which the error occurred."

*Fix* (Phase 1, see refactor plan): introduce
~DiceHistoryError~ with variants ~ReadError { path, source }~,
~WriteError { path, source }~, ~ParseError { path, source }~,
~RenameError { from, to, source }~.

** Code structure (orchestrator main.rs, sibling files) — *PASS*

Server's ~main.rs~ is 157 lines and delegates correctly.  CLI
~main.rs~ is 54 lines, similar pattern.

** OpenAPI / aide instrumentation — *PARTIAL FAIL*

~web_base.rs~ uses ~ApiRouter~ + ~api_route~ + ~scalar::Scalar~
correctly.  But the ~dice.rs~ ~Router~ is plain axum — it isn't
in the schema at ~/api-docs/openapi.json~ and isn't browsable
in ~/scalar~.

*Fix*: convert ~dice::router()~ to return ~ApiRouter<AppState>~
and use ~api_route(...)~ for all three endpoints.  Same for
the upcoming compendium routes.

** Type-driven validation, no Option-creep — *PASS WITH RISK*

~CliRaw~ → ~ConfigFileRaw~ → ~Config~ stage is correctly
modeled in ~config.rs~.

*Risk*: when the compendium and encounter persistence land,
we'll be tempted to use ~Option<String>~ for fields that are
required-after-validation.  COMPENDIUM_PLAN already specifies
separate ~Creature~ + ~CreatureDraft~ types; extend the same
discipline to ~Encounter~ vs ~EncounterDraft~ when persistence
lands.

** Async runtime + mutex choice — *PASS*

~tokio~ with ~tokio::sync::Mutex~ in ~dice.rs~.  Atomic-rename
write pattern (write to temp + rename) is in place.

** Systemd integration + graceful shutdown — *PASS*

~systemd::notify_ready()~ called after bind.
~serve(...).with_graceful_shutdown(shutdown_signal())~ handles
SIGTERM/SIGINT.

** Frontend layering: rules vs view — *PARTIAL FAIL*

Compliant in spirit: ~Encounter.elm~, ~Dice.elm~, ~HpChange.elm~
import nothing from ~Html~ / ~Browser~ / ~Url~.

*Gap*: the rules-engine modules have ballooned.  ~Encounter.elm~
is 1,545 lines and now contains five distinct subsystems
(turn lifecycle, death saves, conditions, save notices, timer
ticks, roster mutation).  Splitting into submodules without
breaking the layering rule preserves the discipline AND
restores reviewability.

** No handwritten JS — *PASS*

Only ~public/elm.js~ (compiled output) and a tiny bootstrap
~index.html~ exist; no hand-rolled glue.  The recent ~ping.wav~
audio asset is the first non-Elm runtime dependency, and it's
declarative (~<audio src="/ping.wav" autoplay>~), not imperative.

** CSS discipline (flat selectors, custom properties, dark mode) — *PASS WITH RISK*

CSS uses ~:root~ custom properties + ~@media (prefers-color-scheme:
dark)~ override, matching the template.

*Risk*: ~style.css~ is now 2,179 lines and growing.  Several
recent additions (memo pill, timer pill, save notice, condition
chip) repeat the same chip / pill pattern.  Extract a base
~.pill~ class with modifier classes; reduce surface area by
~30%~.

** Tests — *FAIL*

No ~tests/~ directories on either crate.  No ~elm-test~ setup.
Template contract violated.

*Fix*: Phase 4 introduces ~elm-test~ for the four pure modules
and integration tests on the server crate's mutation routes.

** Documentation conventions — *PASS WITH GAPS*

~README.org~ exists, ~CHANGELOG.org~ exists,
~docs/ARCHITECTURE.md~ exists, ~CONTRIBUTING.org~ exists,
~llms.org~ exists.

*Gaps*:
- ~docs/ARCHITECTURE.md~ is Markdown; template prefers
  ~.org~.  Not a blocker, but inconsistent with the rest.
- ~CHANGELOG.org~ has been growing under one big "Upcoming"
  heading; ~changelog-roller~ (in our flake inputs!) expects a
  specific shape to roll a release.  Worth verifying we aren't
  one bad section away from a broken release roll.

** Pre-commit hook + treefmt — *PASS*

Hook is symlinked at shell entry (visible in ~flake.nix~);
treefmt formats .rs / .nix / .elm / .css on commit.  Recent
commits show this working (occasional re-format then re-stage
during a commit).

*** Collapse the ~with*Ui~ helpers

We currently have *six near-identical* helpers: ~withDice~,
~withHpChange~, ~withInitiative~, ~withNoteEdit~,
~withConditionUi~, ~withMemoEdit~, ~withTimerSetup~ (plus
~withEncounter~ which is genuinely different).  All six follow
the pattern:

#+begin_src elm :results none :exports code
withFoo : (FooUi -> FooUi) -> Model -> Model
withFoo fn model =
    case model.foo of
        Just ui ->
            { model | foo = Just (fn ui) }
        Nothing ->
            model
#+end_src

Replace with a single primitive:

#+begin_src elm :results none :exports code
-- Util/Maybe.elm
mapMaybe : (a -> a) -> Maybe a -> Maybe a
mapMaybe = Maybe.map
#+end_src

…and inline at call sites:

#+begin_src elm :results none :exports code
{ model | dice = Maybe.map fn model.dice }   -- when DiceUi becomes Maybe-wrapped
#+end_src

…or, where the modal state is currently *not* Maybe-wrapped
(~DiceUi~ for the dice modal is always present, with an ~open~
field), make it Maybe-wrapped for consistency.  Net deletion:
~50 lines, plus the seven helpers go away.

*** Extract ~viewModal~

All seven modals share this skeleton:

#+begin_src elm :results none :exports code
div [ class "modal-backdrop", onClick CloseFoo ]
    [ div
        [ class "modal modal--foo"
        , stopPropagationOn "click" (Decode.succeed ( NoOp, True ))
        , attribute "role" "dialog"
        , attribute "aria-modal" "true"
        , attribute "aria-label" "..."
        ]
        [ div [ class "modal__header" ]
            [ div [ class "modal__title" ] [ text "..." ]
            , button
                [ class "modal__close"
                , onClick CloseFoo
                , title "Cancel"
                , attribute "aria-label" "Cancel"
                ]
                [ text "×" ]
            ]
        , div [ class "modal__body" ] [ {- per-modal -} ]
        ]
    ]
#+end_src

Extract:

#+begin_src elm :results none :exports code
-- View/Modal.elm
view :
    { close : msg
    , title : String
    , extraClass : String
    , body : List (Html msg)
    }
    -> Html msg

Net deletion: ~150 lines across the seven modals, identical
behavior.  Bonus: the Esc-key handler also moves into the
helper, ending the per-modal ad-hoc subscription dance.

** Backend

*** Replace ~std::io::Result~ in ~dice.rs~

#+begin_src rust :results none :exports code
#[derive(Debug, Error)]
pub enum DiceHistoryError {
    #[error("Failed to read dice history file at {path}: {source}")]
    ReadError { path: PathBuf, source: std::io::Error },

    #[error("Failed to write dice history file at {path}: {source}")]
    WriteError { path: PathBuf, source: std::io::Error },

    #[error("Failed to atomically rename {from} -> {to}: {source}")]
    RenameError { from: PathBuf, to: PathBuf, source: std::io::Error },

    #[error("Failed to parse dice history JSON in {path}: {source}")]
    ParseError { path: PathBuf, source: serde_json::Error },
}
#+end_src

…and change all internal helpers to ~Result<_, DiceHistoryError>~
with ~?~ propagation.  The HTTP handler maps to ~StatusCode~ via
~impl IntoResponse for DiceHistoryError~.

*** Decorate routes with aide

~dice::router()~ should return ~ApiRouter<AppState>~ instead of
~axum::Router<AppState>~, and each route should use
~api_route(path, handler.into_api_route())~ so the schema picks
them up.  Same when compendium routes land — *do not introduce
a second plain Router*.  Document this in
~docs/ARCHITECTURE.md~'s "Where to put things" table.

*** Extract a shared ~JsonFileStore<T>~ pattern

The dice-history store and the upcoming compendium store will
both want: load on demand, atomic-rename writes, async-mutex'd
read-modify-write, semantic errors.  Lift the common shape into
~crates/lib/src/json_file_store.rs~:

#+begin_src rust :results none :exports code
pub struct JsonFileStore<T> {
    path: PathBuf,
    cache: tokio::sync::Mutex<T>,
}

impl<T> JsonFileStore<T>
where
    T: Serialize + for<'de> Deserialize<'de> + Default + Clone + Send,
{
    pub async fn load_or_default(path: PathBuf) -> Result<Self, JsonFileStoreError>;
    pub async fn read(&self) -> T;
    pub async fn mutate<F, R>(&self, f: F) -> Result<R, JsonFileStoreError>
    where F: FnOnce(&mut T) -> R;
    pub async fn replace(&self, value: T) -> Result<(), JsonFileStoreError>;
}
#+end_src

~DiceHistoryStore~ becomes ~JsonFileStore<Vec<Roll>>~ with
domain helpers (~append~, ~clear~) on top.
~CompendiumStore~ becomes ~JsonFileStore<Vec<Creature>>~ with
its own surface.  Both pick up the ~load_or_bootstrap~ pattern
when we generalize.

Mirror the file-per-concern pattern of ~auth.rs~ / ~dice.rs~
when adding compendium / encounters / users / sessions /
preferences.  Avoid the temptation to roll persistence,
handlers, and types into one module.  Suggested shape:

* Refactor plan (phased)

Each phase is independently shippable, leaves the app in a
working state, and is small enough to review.

** Phase 0 — Tooling (DONE in this commit)

- Add ~d2~ to ~flake.nix~ devPackages.
- Create ~docs/diagrams/~ with the future-state ER diagram
  (~data-model.d2~ + rendered ~data-model.svg~).
- Document the d2 workflow here and in
  ~docs/ARCHITECTURE.md~.

** Phase 1 — Server compliance fixes

1. Convert ~dice.rs~ to use ~DiceHistoryError~ with semantic
   variants.  No behavior change; HTTP handler maps the new
   error type to ~StatusCode~ via ~impl IntoResponse~.
2. Convert ~dice::router()~ to ~ApiRouter<AppState>~ so the
   three endpoints appear in ~/api-docs/openapi.json~ and
   ~/scalar~.
3. Move CHANGELOG entry to a new dedicated section.

Verification: ~cargo test --workspace~ passes; ~/scalar~ shows
the dice routes; manual test of all three endpoints still
works.

** Phase 2 — Frontend domain split

1. Carve ~Encounter.elm~ into:
   - ~Encounter.elm~ (root, types + queue + ~nextTurn~)
   - ~Encounter/DeathSaves.elm~
   - ~Encounter/Conditions.elm~
   - ~Encounter/SaveNotice.elm~
   - ~Encounter/Timer.elm~

   re-exports, narrowed in a follow-up.

Verification: ~elm make~ green; encounter behavior unchanged

** Phase 3 — Frontend view + update split

1. Extract ~Util/Keyboard.elm~ (~enterKey~, ~escKey~).
2. Extract ~View/Modal.elm~ with ~viewModal~ helper.  Migrate

5. Carve ~Main.elm~ into ~Main~ / ~Model~ / ~Msg~ / ~Update~ +

   Compile-driven; one feature per commit.

Verification: ~elm make~ green; per-feature smoke test after
each commit.  Goal: ~Main.elm~ < 200 lines after the last
commit.

** Phase 4 — Tests

1. ~elm-test~ added to ~elm.json~ test deps;
   ~frontend/tests/~ directory with one file per pure module:
   - ~tests/EncounterTest.elm~ — ~nextTurn~, surprise skip,
     dead skip, death-save thresholds, condition lifecycle.
   - ~tests/DiceTest.elm~ — ~parse~ on the existing fixture
     set; ~scan~ on stat-block prose.
   - ~tests/HpChangeTest.elm~ — damage / heal / temp HP / temp
     soak / revive / max-clamp.
   - ~tests/CompendiumTest.elm~ (when that module lands) —
     ~parseStatBlock~ against the real-fixture corpus.
2. Server crate: integration tests in ~crates/server/tests/~
   for ~/api/dice/history~ (full CRUD round-trip with a
   tempfile-backed store) and the upcoming compendium routes.
3. ~justfile~ recipe: ~just test~ runs ~elm-test~ then
   ~cargo test --workspace~.

Verification: Both suites green; CI workflow (Phase 8) gates
PRs on this.

** Phase 5 — Shared file-store abstraction

1. Create ~crates/lib/src/json_file_store.rs~ with
   ~JsonFileStore<T>~ + ~JsonFileStoreError~.
2. Refactor ~dice::DiceHistoryStore~ to be a thin wrapper
   around ~JsonFileStore<Vec<Roll>>~.
3. Verify behavior unchanged via the integration tests from
   Phase 4.

** Phase 6 — Compendium implementation

Per COMPENDIUM_PLAN.org, with these adjustments:
- Use ~JsonFileStore<Vec<Creature>>~ from Phase 5 as the
  storage backend.
- Use ~ApiRouter~ for all routes.
- Move ~Creature~ to ~crates/lib/src/compendium/~ so the CLI
  can also use it for import/export commands.
- Frontend ~Compendium.elm~ lands as a new pure domain module
  next to ~Encounter.elm~ / ~Dice.elm~ / ~HpChange.elm~,
  following the same layering rule.
- Browser modal goes through ~View/Modal.elm~ from Phase 3.
- Add-to-queue handoff lives in ~Update/Compendium.elm~.

** Phase 7 — Future-feature scaffolding

These are the data-model boxes from the diagram that *don't* yet

* Future-feature scaffolding considerations

Each of these maps to a box on the diagram and is in scope for
this plan only as a *shape constraint* — we don't build any of
them here, but the refactor needs to leave room for them.

** Identity / users / sessions

OIDC scaffolding already exists in ~auth.rs~.  Missing:
- ~users~ table to materialize a user record on first login
  with a stable internal ~uuid~.  Until then, ~user_id~ on
  every other table can't be a real FK.
- Role enum (~admin~ / ~dm~ / ~player~) + ~require_role(Admin)~
  middleware.  Compendium write routes will gate on this in
  v2; today they're open.
- Session storage: today's ~MemoryStore~ from
  ~tower-sessions~ is fine for single-instance hosting.  When
  we want HA / multi-replica, swap to a SQLite-backed store
  (or sled).  Not blocking.

** Per-user UI preferences

Stored as a denormalized ~jsonb~ blob on the user (column
~preferences~ on ~user~).  Fields anticipated today:

- ~theme~ (~system / light / dark~)
- ~card_density~ (~compact / regular / spacious~)
- ~sound_enabled~
- ~default_compendium_sort~
- ~keyboard_shortcuts~ (map of action → key)
- Per-feature opt-in/out toggles (e.g. "auto-scroll active card",
  "auto-roll initiative on add")

The ~jsonb~ shape is intentional — adding a new pref doesn't
require a migration.

** Encounter persistence + snapshots

Today ~Encounter~ is in-memory only.  Persisting it requires:
- ~encounter~ table keyed on ~uuid~, owned by a user, with
  ~state~ as a full ~jsonb~ snapshot of the Elm
  ~Encounter.Encounter~ value.
- ~encounter_snapshot~ for periodic auto-saves and manual undo
  points.  Append-only; cleanup policy TBD (LRU / time-based).
- Frontend gets a "Save Encounter" / "Load Encounter" pair of
  modals that browse the user's ~/api/me/encounters~ list.

** Encounter templates

Distinct from saved encounters: a *template* is a pre-built
list of "creature ID × count" that the GM can drop into a fresh
encounter.  Templates are shareable; saved encounters are
private state.  Schema reflects the distinction.

** CR difficulty calculator

Pure function with no persistence:

#+begin_src rust :results none :exports code
pub fn encounter_difficulty(
    party: &[CharacterLevel],
    monsters: &[CreatureRef],
) -> Difficulty
#+end_src

Frontend mirrors it in Elm for live preview.  No HTTP route —
the library function is shared between CLI (~ezpz-dndz-cli
calc-difficulty~) and frontend (when we land the calculator
in the compendium browser).

** Combat log / observability

Today ~hpChangeLog~ is a 10-entry in-memory FIFO on the
client.  Promoting it to a server-backed log per encounter
gives:
- Persistence across sessions / page reloads.
- Multi-DM visibility (the eventual co-DM mode).
- Query surface ("show me Brakka's worst round" / "rolls in
  the last 5 minutes").

Schema: ~combat_log_entry~ rows scoped to ~encounter_id~,
append-only, ordered by ~created_at~.

* Open questions

These are deliberately left for the human:

1. *Data store choice for Phase 7.*  The plan assumes
   ~JsonFileStore<HashMap<UserId, Encounter>>~ for early
   encounter persistence — easy and consistent with dice
   history.  When do we switch to SQLite?  My suggestion:
   either when we need transactions across tables (compendium
   + encounter atomic update) or when single-user encounter
   counts exceed ~hundreds (file size, mutex contention).
2. *Encounter snapshot retention policy.*  Default: keep last
   20, plus all snapshots tagged ~manual~ or ~undo_point~.
   Open to other defaults.
3. *Auto-snapshot cadence.*  Every Next Turn click is the
   safe answer.  We could throttle (one per 30 seconds) if
   storage becomes a concern.
4. *Where does the CR calculator live in the UI?*  Suggested:
   inside the compendium browser, in a small pane that updates
   live as the GM picks creatures to add to the next encounter.
   Alternative: standalone tool in the encounter title bar.
5. *Public-deployment hardening.*  When we go beyond
   homelab-scale: rate limiting (~tower-governor~), CSRF
   tokens on mutation routes, secret rotation playbook,
   backup strategy for ~<data_dir>~.  All worth a separate
   plan when the moment comes.
