#+title:     Modal migration plan
#+language:  en

Status: proposal, not yet scheduled.  This document records the plan for moving
the frontend away from modal dialogs, prompted by external review feedback.
Nothing here is implemented; when work begins, each phase should land as its own
change set.

* Why step away from modals

The app is a live combat tracker: the encounter queue — initiative order, HP,
conditions, whose turn it is — is the one surface a GM needs visible at all
times, and every modal covers it.  Applying damage through a modal hides the
other creature cards; opening the Compendium hides the fight.  A tool whose
purpose is "less bookkeeping, more attention on the table" should not repeatedly
blank the table.

The supporting reasons:

- Modal flows cost open → act → close on actions that repeat dozens of times per
  session.
- The ~Modal~ ADT enforces one open modal, so switching tools mid-flow loses or
  hides in-progress work.
- Modals are the hardest common widget to make accessible (focus traps, escape
  handling, scroll locking, screen-reader announcement).
- On a tablet propped at the table, modals are especially clumsy.
- Current design guidance treats modals as a last resort for genuine
  interruptions, not as the default container for features.

* The tiered policy

Rather than a flat ban, each surface uses the least disruptive pattern that fits
it:

1. *Inline* on the creature card — for high-frequency, per-creature actions.
   Extends the existing inline-edit idiom (AC, max HP).
2. *Popover* anchored to the triggering control — for small, pick-one
   interactions.
3. *Docked panel / drawer* in the right rail — for combat tools that need real
   estate but must not hide the queue.
4. *Route / full page* — for destinations: prep-time surfaces that do not need
   the encounter on screen at all.
5. *Toast + undo* — replacing blocking confirmations with reversibility.

A true modal remains acceptable only for a destructive, must-decide-now
interruption, and the toast + undo pattern should eliminate most of those.

* Mapping

Every entry in =frontend/src/View/Modal/= and its target pattern.

** Inline on the creature card

- =HpChange= (Damage / Heal / Temp HP) :: The card expands an input row in
  place, so the queue stays visible while typing.  The ten-entry log shrinks to
  "last change + undo" on the card; the full log lives in the dice panel.
- =Condition= :: The same expansion: condition grid, duration, and save-to-end
  controls in an expanded card section, with "apply to selected" as a checkbox.
  The biggest inline candidate and the biggest payoff: conditions get set while
  watching the fight.
- =Memo= (the row-three note) :: Clicking the icon becomes an in-place text
  input; no surface at all.
- =Note= (the name note) :: Identical treatment, completing the existing
  inline-edit idiom.

** Popover anchored to the trigger

- =AbilitySave= :: Already receives click coordinates and behaves like a popup;
  formalize it as an anchored popover (roll / advantage / disadvantage) outside
  the modal ADT.
- =Duplicate= :: Already a dropdown menu; reclassify it out of the modal system.
- =QuickAdd= :: Anchored popover under the button with a search box and a
  capped-height scroll; the alpha/CR toggle stays in its header.
- =Initiative= :: Popover anchored to the clicked initiative badge; the
  roll-and-sort buttons and manual entry are one-shot actions that do not
  justify a full-screen interrupt.
- =Timer= :: Small anchored popover at the clock icon; two fields and a radio
  group.

** Docked panel / drawer

- =Dice= :: The strongest panel candidate — a GM plausibly wants it persistently
  open.  Dock it in the right rail below (or tabbed with) the stat block.
- =SaveChain= :: Operates on selected creatures across the queue, so
  inline-on-one-card is wrong and hiding the queue is worse.  A right-rail panel
  lets fail/pass results land visibly on the cards.
- =Treasure= (the roller) :: Rolls against the current queue's enemies; a drawer
  keeps them visible while results generate.
- =CrCalculator= :: Reads the live queue by design; as a panel, the difficulty
  updates visibly as creatures are added or removed.
- =RandomEncounter= :: Its entire output is creatures appearing in the queue; a
  drawer means seeing them land.
- =SpellList= :: Reference material consulted mid-combat; a drawer or a tab in
  the tool panel beats either a modal or a separate page.
- =Save= :: Split.  A one-click quick-save button in Encounter Controls (toast
  confirmation) covers the common case; the "save as" form becomes a small
  drawer; full file management moves to the =/saves= route below.

** Route / full page

- =Compendium= (browser) :: The flagship conversion: a =/compendium= section.
  It is a database UI, not an interruption, and its selection-plus-detail layout
  wants the space.
- =CompendiumEdit= :: =/compendium/edit/:id=.  The deepest form in the app; a
  page gives it room and normal browser behavior (back button, refresh-safe).
- =CompendiumPaste= :: A step under the compendium route; paste → parse preview
  → save is a linear flow suited to a page.
- =GroupEdit= :: Nested compendium route; group building is prep work.
- =LoreEdit= :: Nested compendium route.
- =TreasureTable= (the table editor, distinct from the roller) :: Prep-time
  editing of reference data; the roller drawer links to it.
- =Load= :: A =/saves= management page (rename, delete, server/local), with a
  lightweight "recent saves" popover on the Load button for the common case.
- =SaveCompendium= / =LoadCompendium= :: Fold both into the compendium route as
  its import/export screen; they share the file-management shape of encounter
  save/load.

** Toast + undo

The Reset and Clear confirmations, and the overwrite confirmation inside Save,
become non-blocking toasts with an Undo action.  Faster at the table, and it
removes the last must-answer-now surfaces — which is what makes the policy
workable without an escape hatch.

* Sequencing

1. Rename the ~Modal~ ADT to a ~Surface~ ADT with ~Inline~ / ~Popover~ / ~Panel~
   / ~Route~ variants.  Pure refactor, no behavior change; every later phase
   builds on it.
2. Convert the combat-critical four — =HpChange=, =Condition=, =SaveChain=,
   =Dice= — which deliver nearly all the at-the-table value.
3. Move the compendium family (browser, editor, paste, groups, lore,
   import/export) to routes.
4. Sweep the small popovers and the toast + undo conversions last.

The =Update/*= modules barely change throughout: this is almost entirely
=View/*= and ~Model.modal~ plumbing, which is what the frontend layering (see
[[file:ARCHITECTURE.org][ARCHITECTURE.org]]) was built to absorb.  The panel-based layout is also
effectively the second UI layout the domain/view split was designed to enable.
