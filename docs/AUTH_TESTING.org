#+title:     Testing user accounts in local dev
#+language:  en

This file is a quick reference for poking at the user-account feature
locally — register, log in, watch the session cookie, see per-user
data isolation in action.  It assumes the backend is already running
under ~just dev~ or equivalent, and that you have ~curl~ + ~jq~ on
PATH (both come with the Nix dev shell).

* What's wired up

| Layer                          | Status                          |
|--------------------------------+---------------------------------|
| User store + Argon2id hashing  | shipped (commit ~b5341cd~)      |
| Register / login / logout / me | shipped — ~/api/auth/*~          |
| ~require_auth~ on /api/*       | shipped — every non-auth route  |
| Per-user encounter + saves     | shipped (commit ~3b0220a~)      |
| Per-user dice history          | *not yet* — shared across users |

* Setup

#+begin_src sh :exports code
just dev   # starts the server on http://127.0.0.1:4040
#+end_src

Or, if you want a clean slate isolated from your usual dev data:

#+begin_src sh :exports code
mkdir /tmp/auth-scratch
nix develop --command \
  cargo run -p ezpz-dndz-server -- \
    --listen 127.0.0.1:4040 \
    --data-dir /tmp/auth-scratch \
    --base-url http://127.0.0.1:4040 \
    --frontend-path frontend/public
#+end_src

In another shell:

#+begin_src sh :exports code
COOKIES=/tmp/ezpz-cookies.txt
rm -f "$COOKIES"
BASE=http://127.0.0.1:4040
#+end_src

* Smoke test the auth flow

** Register a user

#+begin_src sh :exports code
curl -s -c "$COOKIES" \
  -X POST "$BASE/api/auth/register" \
  -H 'content-type: application/json' \
  -d '{"email":"alice@example.com","password":"hunter2hunter","display_name":"Alice"}' \
  | jq
#+end_src

Expected: 201, body
~{"id":"<uuid>","email":"alice@example.com","display_name":"Alice","created_at":<unix>}~.
The session cookie ~id=…~ is now in =$COOKIES=.

** Identify yourself

#+begin_src sh :exports code
curl -s -b "$COOKIES" "$BASE/api/auth/me" | jq
#+end_src

Expected: 200 + the same user record.

** Hit a protected route

#+begin_src sh :exports code
curl -s -b "$COOKIES" "$BASE/api/encounter" | jq
#+end_src

Expected: 200, body ~null~ (no encounter saved yet).

Without the cookie:

#+begin_src sh :exports code
curl -i "$BASE/api/encounter"
#+end_src

Expected: 401 + ~{"error":"Invalid email or password"}~.

** Save and read back

#+begin_src sh :exports code
# Persist a live encounter for Alice.
curl -s -b "$COOKIES" -X PUT "$BASE/api/encounter" \
  -H 'content-type: application/json' \
  -d '{"creatures":[],"activeName":"Brakka","round":3}'

# Read it back.
curl -s -b "$COOKIES" "$BASE/api/encounter" | jq
#+end_src

** Log out, then back in

#+begin_src sh :exports code
curl -s -b "$COOKIES" -c "$COOKIES" -X POST "$BASE/api/auth/logout" \
  -w '%{http_code}\n'
# 204

curl -s -b "$COOKIES" "$BASE/api/auth/me" -w '\n[%{http_code}]\n'
# 401

curl -s -c "$COOKIES" -X POST "$BASE/api/auth/login" \
  -H 'content-type: application/json' \
  -d '{"email":"alice@example.com","password":"hunter2hunter"}' \
  | jq
#+end_src

* Verify per-user isolation

The most important assertion: Bob can't see Alice's saves.

#+begin_src sh :exports code
ALICE=/tmp/alice-cookies.txt
BOB=/tmp/bob-cookies.txt
rm -f "$ALICE" "$BOB"

# Two independent users.
curl -s -c "$ALICE" -X POST "$BASE/api/auth/register" \
  -H 'content-type: application/json' \
  -d '{"email":"alice@example.com","password":"hunter2hunter","display_name":"Alice"}' \
  > /dev/null

curl -s -c "$BOB" -X POST "$BASE/api/auth/register" \
  -H 'content-type: application/json' \
  -d '{"email":"bob@example.com","password":"hunter2hunter","display_name":"Bob"}' \
  > /dev/null

# Alice creates a save.
curl -s -b "$ALICE" -X PUT "$BASE/api/encounter/saves/Goblin%20Ambush" \
  -H 'content-type: application/json' \
  -d '{"creatures":[{"name":"Goblin"}],"round":1}'

# Bob lists his saves — should be empty.
echo "--- Bob's saves ---"
curl -s -b "$BOB" "$BASE/api/encounter/saves" | jq

# Bob can't fetch Alice's save by name.
echo "--- Bob tries Alice's save ---"
curl -s -b "$BOB" "$BASE/api/encounter/saves/Goblin%20Ambush" \
  -w '[%{http_code}]\n'
# 404

# Both users can have a save with the same name without conflict.
curl -s -b "$BOB" -X PUT "$BASE/api/encounter/saves/Goblin%20Ambush" \
  -H 'content-type: application/json' \
  -d '{"creatures":[],"round":1}' \
  -w '[%{http_code}]\n'
# 200
#+end_src

The same isolation applies to compendium-saves
(=/api/compendium/saves/...=).  Try it with a similar pair.

* Inspect the on-disk shape

The user records:

#+begin_src sh :exports code
jq . /tmp/auth-scratch/users.json
#+end_src

Each record has =id= (UUID), =email=, =password_hash= (Argon2id PHC
string — ~$argon2id$v=19$...~), =display_name=, =created_at= (unix
seconds).

Per-user saves:

#+begin_src sh :exports code
jq 'keys' /tmp/auth-scratch/encounter-saves.json
# [ "<alice-uuid>", "<bob-uuid>" ]

jq 'keys' /tmp/auth-scratch/compendium-saves.json
#+end_src

Live encounter:

#+begin_src sh :exports code
jq 'keys' /tmp/auth-scratch/encounter.json
#+end_src

Each is keyed by the user's UUID; values are the user's data.

* Validation errors to watch

| Input                                | Expected                       |
|--------------------------------------+--------------------------------|
| ~password~ <8 chars                  | 400, "Password must be …"      |
| ~email~ without ~@~ or ~.~ in domain | 400, "Email must look like …"  |
| empty ~display_name~                 | 400, "Display name must not …" |
| duplicate ~email~                    | 409, "Email is already …"      |
| wrong password on login              | 401, "Invalid email or …"      |

Email comparison is case-insensitive; ~Alice@Example.COM~ collides
with ~alice@example.com~ on the second registration attempt.

* Resetting accounts

There's no admin UI yet.  To wipe everything:

#+begin_src sh :exports code
rm -f /tmp/auth-scratch/users.json /tmp/auth-scratch/encounter*.json \
      /tmp/auth-scratch/compendium-saves.json
#+end_src

The server soft-fails on missing files (~JsonFileStore::load_or_default~);
restart the server and the next register call recreates them.

To delete *one* user, edit =users.json= directly — drop their record
from the array.  That orphans their saves under their UUID; if you
also want those gone, edit =encounter*.json= and =compendium-saves.json=
to drop the entry under their UUID key.

* What's missing

** Frontend login / register UI

Right now the SPA at ~http://127.0.0.1:4040/~ doesn't know about
authentication.  When you load the page in a browser without a
session, every API call fails with 401, and the UI just shows
empty / broken state — no login screen.  Two ways to bootstrap a
session today:

1. *curl-assisted.*  Run the register flow above to drop a session
   cookie into your browser.  Easiest path: register via curl, then
   in the same browser session, open dev-tools → Application →
   Cookies → manually paste the ~id=…~ cookie (matching the path
   ~/~).  Reload the page.  The SPA fetches /api/auth/me, sees
   200, and the rest of the API calls succeed.

2. *Direct API.*  Some browsers' fetch playgrounds let you POST
   ~/api/auth/login~ from the page itself; the response sets the
   cookie automatically and a refresh boots the app authenticated.

The frontend integration (login form, register form, logout
button, and 401-handling redirect) is the next phase of work and
intentionally not in scope for this commit cycle.

** Per-user dice history

Dice history is still shared — every user sees every roll.  Low
risk because the records are anonymous numbers, but if your usage
involves multiple unrelated DMs running combat at the same time
and not wanting to see each other's noise, scope this next.

** Email verification + password reset

Both require an SMTP setup that the project doesn't have.  Add
once you've decided how mail is going to work in your homelab —
maybe via a relay through ~msmtp~ or whatever your existing setup
uses.
