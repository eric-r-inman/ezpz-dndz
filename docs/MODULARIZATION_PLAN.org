* Human summary

The frontend has outgrown its single-file-per-domain layout.
=Main.elm= is now ~9,300 lines with 159 ~Msg~ constructors, one
3,000-line ~updateInner~, and 250+ view functions; the prior
[[file:archive/OPTIMIZATION_AND_COMPLIANCE_PLAN.org][prior May plan, archived]]
called for splitting it but only the seed beachhead landed
(=View/Modal.elm=, =View/Chip.elm=, =View/StatBlock.elm=, plus
=Encounter/DeathSaves.elm= / =SaveNotice.elm= / =Wire.elm=).  In
the meantime ~Main.elm~ has *grown* by ~60% as the compendium and
encounter persistence shipped.  This plan finishes the split,
extracts the persistent grime (modal frame duplication, =with*Ui=
helper sprawl, scattered ~Cmd~ wiring), reshapes a few data
models that have outgrown their first form (creature identity,
modal UI state, the ad-hoc ~Cmd~ dispatch), and lays the
scaffolding for the next round of features (per-user encounters,
preferences, role-gated mutations, co-DM WebSockets) so each
lands in its own module instead of as another screenful of
~Main.elm~.

The plan is *eleven phases*, each independently shippable
(compile + tests + smoke pass) and small enough to commit-and-move-on.
The ordering is: cheap mechanical wins first (Phases 1–2), then
domain submodule splits where boundaries already exist (3–4),
then the big ~Main.elm~ carve-up (5–7), then CSS/data/effects
hygiene (8–10), and ending with a server-side compliance pass
(11).  Total estimated diff: ~+2000 / −9000 lines spread across
~50 commits, with the entire app behavior unchanged from the
user's perspective.

The plan assumes I will execute it autonomously: every phase
ends with =cargo test --workspace= + =elm-test= + a manual
smoke check via =just dev=, and commits but does NOT push (push
is denied per [[file:../.claude/settings.json][.claude/settings.json]]).
On every phase boundary I'll commit progress so the user can
review the chain at the end.

* Constraints (do not violate)

These are durable from CLAUDE.md, the rust-template, and the
existing ARCHITECTURE.md layering rule.  Treat as hard limits.

** Frontend
- *No ~Html~ / ~Browser~ / ~Url~ imports in domain modules.*
  Domain = =Encounter*=, =Dice*=, =HpChange=, =Compendium*=
  (everything but =Main=, =View/*=, =Update/*=).  Compiler
  enforces.
- *Pure update branches as one-liners.*  Rules-y work
  (queue walks, HP arithmetic, condition lifecycle) belongs
  in domain modules.  ~update~ delegates.
- *No handwritten JS.*  Everything reaches DOM via Elm.  The
  one allowed escape hatch is declarative (~<audio
  src=...>~).  Don't introduce ports unless the feature
  absolutely requires it; document the necessity if so.
- *Type-driven validation.*  Modal UI state with raw strings
  is fine ("transient typing isn't clamped"); but stages need
  distinct types (Draft → Form → Validated).  Don't reach
  for ~Maybe~ on fields that are required-after-validation —
  introduce an intermediate type instead.
- *Pascal Initialisms in new identifiers* (=Url=, not =URL=;
  =Db=, not =DB=).
- *No ~loop~/early ~return~* preferred where Elm provides
  combinators; small extracted helpers > deep nesting.

** Backend (Rust)
- *Semantic ~thiserror~ variants.*  Don't expose
  ~std::io::Result~ from a public API; wrap into a
  ~XReadError { path, source }~ / ~XWriteError~ / etc. that
  identifies the *operation*, not just the kind.
- *~main.rs~ is an orchestrator.*  Sibling files own concerns
  (config, logging, etc.).  No business logic in =main.rs=.
- *~aide::ApiRouter~ for every HTTP route* so OpenAPI stays
  complete.  No second plain ~axum::Router~.
- *Use ~JsonFileStore<T>~ for persistence-backed features.*
  Don't roll a one-off file store.
- *Errors propagate; do not swallow.*  Internal helpers use
  ~?~; HTTP handlers map to ~StatusCode~ at the boundary via
  ~impl IntoResponse~.

** Repo / docs
- *New docs go in =docs/= as =.org= files.*
- *No file lists in documentation prose.*  Tables and
  pointers are fine.
- *Comments must be complete sentences, wrapped at 80 cols.*

** Tests
- *Tests must exit with proper error codes.*  =elm-test= and
  =cargo test --workspace= both honor this.
- *Integration tests preferred over unit tests on contrived
  scenarios.*  Real backends, real HTTP, real file system
  (=tempfile= crate for paths).

In priority order:

1. *Reviewability.*  Any single file should fit in a screenful or
   two of any reasonable IDE.  Target cap: 600 lines / module
   (excluding cohesive parsers and codecs which can be larger).
2. *Functional purity.*  Domain modules stay pure (no ~Cmd~,
   no ~Html~).  Update logic stays a thin dispatcher; Cmd-emitting
   work goes through dedicated helpers in =Update/Effects.elm=.
3. *Modularity by feature.*  Each feature (Dice, HpChange,
   Initiative, Condition, Note, Memo, Timer, Compendium, Toast,
   Lifecycle, Auth) gets its own =Update/Foo.elm= +
   =View/Foo.elm= + (where applicable) =Model/Foo.elm= record.
4. *Predictability for future features.*  Each new modal /
   feature should have a clear "go-here" file path before
   anyone writes a Msg.
5. *Migration safety.*  Each phase compiles green at HEAD,
   passes elm-test + cargo test, and is independently
   revertable.  No phase mixes "split feature X" with
   "rewrite feature X" — semantic changes go in their own
   commits.

Functional principles applied throughout:

- *ADTs over Bool flags.*  Where two booleans encode three
  states, replace with an enum.  E.g. modal-open state
  (~modal : Maybe ModalState~) replaces N independent
  ~Maybe SomeUi~ fields.
- *~Maybe a~ at the boundary, real types inside.*  Decoders
  may emit ~Maybe~ for tolerance; domain functions take and
  return concrete records.
- *No partial functions.*  ~Encounter.activeCreature~ today
  returns ~Maybe Creature~ — keep that pattern.  Don't write
  ~Encounter.activeCreatureUnsafe~.
- *Composition over inheritance.*  Multi-target apply is
  ~List.foldl (mapCreature name fn)~, not a generic
  "apply-to-many" trait.  Keep this idiom.
- *Cmd as data, batched.*  ~Update/Effects.elm~ exposes
  ~Cmd Msg~-returning helpers that callers compose with
  ~Cmd.batch~; no inline Http.post calls in update branches.

Modern codebase design touches:

- *Narrow exposes.*  Each module's =module Foo exposing (..)=
  becomes an explicit list.  Forces deliberate API surface.
- *No re-exports.*  When something moves to a submodule,
  callers update their imports.  Re-exports are tolerated as
  a transition step (one phase) but cleaned up in the next.
- *One-screen rule for ~update~ branches.*  If the branch
  body is more than ~10 lines, it should be calling a helper
  in =Update/Foo.elm=.

* Risks & rollback strategy

- *Phases 5–7 have the largest commit churn.*  Mitigation:
  break into many small commits (one file move + reference
  fixes per commit).  =git revert= a single commit if a
  regression appears.
- *Module re-export transitions:* between Phase 3 commits
  3a..3d the encounter root re-exposes moved types.  3e
  removes those re-exports and narrows imports.  If 3e
  introduces a regression, leave 3e reverted; the
  re-exports keep the app working until a re-attempt.
- *Modal ADT (Phase 10b)* is the highest-risk change in the
  whole plan because it touches every modal handler.  Land
  it after Phase 6+7 are done so each modal lives in its
  own module — the mass rewrite is a coordinated swap of
  =model.foo : Maybe FooUi= calls into
  =model.modal == Just (ModalFoo ui)= patterns, scoped to
  per-feature Update/View modules.
- *instanceId rename (Phase 10a)* may need a transition
  commit where =Creature.instanceId == name= for all rows
  before a follow-up commit decouples them; on-disk legacy
  encounters need decoder defaults forever (or a one-time
  migration task documented here).

* Open questions (resolve before / during execution)

1. *Modal ADT timing.*  Phase 10 is late but the ADT change
   is invasive.  Consider front-loading to between Phase 6
   and Phase 7 so view modules can pattern-match on the new
   shape from the start (avoids a rewrite-then-rewrite).
2. *Test backfill scope.*  Phase 10 lists ~40 new tests.
   Rough; trim to highest-value cases if total time budget
   tightens.  Minimum: round-trip Wire tests + Lifecycle
   nextTurn tests.
3. *=cli= compendium commands.*  Will it talk HTTP (server
   must be running) or read the file directly via
   =JsonFileStore::load_or_default=?  File-direct is
   simpler; HTTP gives a single point of authoritative
   server behavior.  Recommendation: file-direct for v1
   (no server dep), wrap behind a trait so HTTP becomes a
   one-line swap when needed.
4. *Per-user persistence rollout.*  Phase 11 lays the
   =/api/me/...= scaffolding but doesn't migrate
   =/api/encounter= or =/api/dice/history= to the namespace.
   Migration is its own follow-up plan once OIDC is wired
   to a real user table.
5. *Domain → View boundary inside =View/Chip.elm=.*  The
   chip helper renders =Encounter.Condition=.  Should it
   import from the domain module or take a flat record?  If
   the latter, every caller adds a mapping step — likely
   not worth the indirection.  Vote: domain import is OK
   because =View/Chip.elm= is itself a view module.
