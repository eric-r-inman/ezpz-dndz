* Summary

The suite played every area of the app as a DM would.  It ran in Chromium and
Firefox.  It found two blockers and 14 major faults among about 110 distinct
issues.  Both blockers are fixed.  One turned up while the suite was being built
and shipped as a fix in v0.35.0.  The other let a sign-in replace the account's
custom creatures and groups.

The suite holds 443 scenarios.  The first full run passed 432 cases and held 156
as known faults.  A known fault is a strict ~xfail~ that names its finding
below.  No case failed.  A finding marked fixed has had its ~xfail~ removed.
Some findings show in more than one area.  A repeat points to its first entry.
The table counts a repeat in each area it shows in.

* How the run worked

Six agents each took one area.  Each wrote its scenarios on the shared page
objects in ~qa/pages/~, ran them in both browsers and read its screenshots.
Each confirmed every known fault against its stated reason.  The blockers and
QA-TURN-01 were also reproduced by hand.  Each blocker was traced to its code.

The suite is not yet free of flakes.  Two of the last 16 full runs with eight
workers each had one case fail once.  Neither failed again on any rerun.  The
next run cleared each one's trace before it was read.

The suite did not cover these:

- Real screen readers.  Names come from the accessibility tree.
- Touch input.  Phone and tablet sizes are emulated with a mouse.
- OIDC sign-in.  It needs an outside provider.
- The CLI's ~harvest~.  It needs the network.
- Postgres.  Every scenario runs on SQLite.
- Safari.  The ~qa~ shell already carries WebKit.  Adding Safari's engine is a
  small step.

** Initiative and turn flow

*** QA-TURN-01: Begin combat leaves Manage HP aimed at nobody

- Status :: fixed
- Severity :: major
- Steps :: Quick Add an Ogre and a Goblin Warrior.  Press Begin combat.  Type 5
  into Manage HP and press Damage.
- Expected :: Manage HP aims at the creature whose turn it is.  The damage
  lands.  ~Model.defaultTarget~ falls back to the active creature.
- Actual :: The target is blank and Damage does nothing.  It stays that way
  until the first Next turn.  ~Update.QuickAdd.appendAtZero~ never calls
  ~Model.reaimStale~.  ~Update.Encounter.run~ does not re-aim the editors
  either.
- Evidence ::
  ~test_begin_combat_aims_manage_hp_at_the_creature_whose_turn_it_is~
- Action :: Fixed.  Quick Add re-aims the editors through ~Model.reaimStale~.
  Begin combat releases the target the way Next turn does.

*** QA-TURN-02: Begin combat gives the first turn to an inactive creature

- Status :: fixed
- Severity :: minor
- Steps :: Mark the top creature inactive with ∅.  Press Begin combat.
- Expected :: The first creature that can act gets the turn.  The ∅ tooltip says
  an inactive creature skips its turn.
- Actual :: The inactive creature becomes active.  ~Encounter.run~ takes the
  head of the queue and runs no turn-start rules.
- Evidence :: ~test_begin_combat_passes_over_an_inactive_top_creature~
- Action :: Fixed.  ~Encounter.Lifecycle.begin~ starts with the first creature
  that passes Next turn's skip test.  It runs that creature's turn-start rules.

*** QA-TURN-03: Removing the active creature skips the turn rules

- Status :: fixed
- Severity :: minor
- Steps :: Remove the active creature in each of three setups.  In the first,
  the next creature is inactive.  In the second, the next creature has spent its
  reaction.  In the third, the active creature is last in the queue.
- Expected :: The same result as pressing Next turn.
- Actual :: The inactive creature takes the turn.  The reaction stays spent.
  The turn wraps to the top of the queue but the round stays the same.
- Evidence ::
  ~test_removing_the_active_creature_passes_over_an_inactive_successor~,
  ~test_removing_the_active_creature_starts_the_successors_turn~ and
  ~test_removing_the_last_creature_on_its_turn_starts_the_next_round~
- Action :: Fixed.  Removing the creature whose turn it is runs Next turn first.

*** QA-TURN-04: A readied action never lapses

- Status :: fixed

** Accounts, persistence and the CLI

*** QA-ACCT-01: Signing in erases the account's own creatures and groups

- Status :: fixed
- Severity :: blocker
- Steps :: Sign in.  Make a custom creature and a compendium group.  Sign out.
  Sign in again through the form.
- Expected :: The creature and the group are still there.
- Actual :: Both are gone.  A toast says "Imported 0 creatures from your
  pre-sign-in session."  Every anonymous page view stores an empty compendium
  snapshot in localStorage.  On the next sign-in ~migrateLocalCompendiumCmd~
  posts it to ~/api/compendium/import~.  The server's ~replace_for_user~ then
  deletes the account's creatures and groups.  With anonymous creatures present,
  they replace the account's own instead of joining them.
- Evidence :: ~test_signing_out_and_back_in_keeps_the_dms_creatures~,
  ~test_signing_in_keeps_the_accounts_own_creatures_and_groups~ and
  ~test_signing_in_with_anonymous_creatures_adds_them_beside_the_accounts_own~
- Action :: Fixed.  Sign-in appends the snapshot's creatures and groups under
  fresh ids and keeps the account's own.  An empty snapshot is skipped.
