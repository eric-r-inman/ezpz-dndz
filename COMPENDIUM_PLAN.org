If you're picking this work up cold, read both documents — the

* Scope

This document plans the next-phase work to add a fully-realized
*compendium* to ~ezpz-dndz~: a creature/stat-block library with full
CRUD, free-text stat-block parsing, import/export, and a clean
hand-off into the encounter queue.

Reference for behavior: ~/dev/dnd-encounter-manager (the legacy
JS project we're porting features from). Reference for structure:
existing layering in ~Encounter.elm~ / ~Dice.elm~ / ~HpChange.elm~
plus the dice-history persistence pattern in
~crates/server/src/dice.rs~.

** Out of scope (for this plan)

- *CR difficulty calculator.* Explicitly excluded by the user.
- *Creature images / token portraits.* Adds binary asset
  handling and storage path complexity. Defer to a follow-up.
- *Spell-slot / legendary-action usage tracking on instances.*
  The old project rendered these but never tracked consumption.
  Defer.
- *Two-way sync between compendium template and live combatant.*
  Old project was one-way (template → instance). We keep that.
- *Encounter persistence.* Already on the existing roadmap as a
  separate item; out of scope here.

* Decisions and assumptions

The following calls were made up-front so the implementation phases
that follow have a single shape to target.

** Storage

- *Single shared compendium per deployment.* No per-user
  compendiums in v1. Per the project's deployment target memory
  ("homelab-scale SaaS … shared compendium + per-user
  encounters").
- *JSON file under ~<data_dir>/compendium/creatures.json~* as the
  storage backend. One file holds the entire compendium. Even at
  many thousands of creatures the file fits comfortably in RAM
  on the server side. SQLite migration is a follow-up; the HTTP
  API shape doesn't change when we swap the implementation.
- *Atomic-rename writes + async mutex* mirroring
  [[file:crates/server/src/dice.rs][crates/server/src/dice.rs]].
- *Bundled creatures embedded via* ~include_str!~ at build time.
  On first launch, if the data file is absent, write the bundled
  set out so the user has something to browse immediately.
- *No "official vs custom" distinction* in the data layer (mirrors
  the old project). All creatures live in the same collection;
  the user can edit / delete bundled ones. A "Reset to Base"
  endpoint restores the bundled set.

** Identity

- *Stable server-generated UUIDs* (~uuid::Uuid::new_v4~) returned
  on insert. Old project used name-based ids which collide when
  two GMs both make a "Custom Goblin"; we avoid that. Names
  remain free-text and may collide.
- The frontend never invents a creature id; it always asks the
  server.

** Auth gating

- All read routes are open (or fall under the existing OIDC
  optional-auth flow).
- Write routes (~POST~ / ~PUT~ / ~DELETE~ / ~/import~ / ~/reset~)
  are open for v1, with a planned ~role=admin~ gate when the
  ~users~ table lands. Documented as a follow-up; no behavior
  change today since OIDC is opt-in in dev.

** Compendium → queue transformation

- *Auto-roll initiative on add.* Old project required manual
  entry; we have the infrastructure (~Dice.batchRollCmd~) so we
  use it. The bulk-add flow rolls one initiative per instance and
  inserts each at the correct queue position via
  ~Encounter.sortByInitiative~.
- *Auto-numbering on multi-add.* Adding "Goblin" while another
  "Goblin" is already in queue produces "Goblin 2", "Goblin 3",
  …. First instance keeps the bare name. Suffix logic mirrors
  the existing ~uniqueCopyName~ helper.
- *Instance-time copy*, not reference. The instance carries a
  ~creatureId : Maybe String~ back-reference to its compendium
  source so the GM can hit "Quick View" and see the full stat
  block, but live combat state is fully self-contained on the
  ~Encounter.Creature~ record. No live sync from template to
  instance.

** Stat-block parser placement

- *Elm-side parser* (~Compendium.parseStatBlock~) using
  ~elm/parser~. Two reasons: (1) keeps the HTTP API minimal — no
  separate parse endpoint; the client posts an already-extracted
  draft. (2) Lets the user see live parse feedback in the paste
  modal without a network round-trip.

Compliance constraints baked into this plan:

- *Routes go on ~ApiRouter<AppState>~*, not plain ~axum::Router~,
  so they appear in ~/api-docs/openapi.json~ and ~/scalar~.
- *All errors are semantic via ~thiserror~* — ~CompendiumStoreError~
  with descriptive variants (~CreatureIdNotFoundError~,
  ~CreatureDuplicateNameError~, ~BundledLoadError~, etc.), never
  bare ~std::io::Error~ propagation.
- *Storage rides on the shared ~JsonFileStore<T>~ abstraction* (see
  Phase 5 of the optimization plan).  No bespoke file IO code; we
  inherit atomic-rename writes + async mutex + load-or-default
  bootstrap from the lib crate.
- *Frontend layering matches ~Encounter~ / ~Dice~ / ~HpChange~* —
  ~Compendium.elm~ imports nothing from ~Html~, ~Browser~, or
  ~Url~.  All view code lives in ~View/~ subdirectories.
- *Stat-block renderer is shared* between the compendium browser
  and the per-card Quick View — written once, consumed twice.

* Data model

** Creature record

The shape we'll commit to. Fields are intentionally flat-ish — the
old project nested everything four levels deep
(~creature.statBlock.armorClass.value~), which is awkward in Elm.

    , kind : CreatureKind                  -- Player / Enemy / Npc

    , damageResistances : List String

    , conditionImmunities : List String
    , senses : Senses

    , xp : Int

    , traits : List Feature

    , reactions : List Feature

    , updatedAt : Int

type Size = Tiny | Small | Medium | Large | Huge | Gargantuan

type alias Speed =
    { walk : Int
    , fly : Int
    , swim : Int
    , climb : Int
    , burrow : Int
    , hover : Bool                         -- "fly 50 ft. (hover)"
    }

type alias Abilities =
    { str : Int, dex : Int, con : Int
    , int : Int, wis : Int, cha : Int
    }

                                          -- collision with Elm's `Int` type
                                          -- name in qualified usage

type alias SkillBonus = { name : String, bonus : Int }

type alias Senses =
    { blindsight : Int                     -- 0 = none
    , darkvision : Int
    , tremorsense : Int
    , truesight : Int
    , passivePerception : Int              -- always set; defaults to 10 + WIS mod
    }

type alias Feature =
    { name : String
    , description : String                 -- raw text; Dice.scan picks out clickable rolls
    , usage : Maybe Usage                  -- "Recharge 5–6", "3/Day"
    }

    = Recharge { low : Int, high : Int }   -- "Recharge 5–6"
    | PerDay Int                           -- "3/Day"
    | PerShortRest Int
    | PerLongRest Int
    | AtWill

type alias LegendaryActions =
    { description : String                 -- preamble: "The dragon can take 3 legendary actions…"
    , uses : Int                           -- usually 3
    , usesInLair : Int                     -- usually 0
    , options : List LegendaryOption
    }

type alias LairActions =
    { initiative : Int                     -- usually 20
    , description : String
    , options : List Feature
    }

type alias RegionalEffects =
    { description : String, effects : List Feature, fadeAfter : String }

type alias Spellcasting =
    { description : String                 -- "The dragon is a 17th-level spellcaster…"
    , ability : Ability
    , saveDc : Int
    , attackBonus : Int
    , atWill : List String                 -- spell names; we don't model the spells themselves
    , slots : List SpellSlotLevel          -- per-slot list; empty for Innate spellcasting
    , innatePerDay : List InnatePerDay     -- "3/day each: …"
    }

type alias SpellSlotLevel = { level : Int, slots : Int, spells : List String }
type alias InnatePerDay = { uses : Int, spells : List String }

type alias CustomSection = { name : String, body : String }

* Stat-block parser

~Compendium.parseStatBlock : String -> Result ParseError CreatureDraft~.

** Input format

Standard 5e Monster Manual stat blocks copied as plain text. The
parser is permissive — it accepts the common variants the user
will encounter when copying from D&D Beyond, the SRD, or other
GM tools.

** Strategy

Section-based, not full grammar:

1. *Header* (lines 1–2):
   - Line 1 = name.
   - Line 2 = ~"<Size> <race> (<subrace>), <alignment>"~ with
     subrace optional.
2. *Core stats block* (looks for keyword markers in order):
   - ~Armor Class N (note)~
   - ~Hit Points N (formula)~
   - ~Speed walk ft., fly N ft., …~
3. *Ability score table* — six numbers + parenthesized modifiers,
   on either two lines (header row + values row) or one
   semicolon-separated row.
4. *Detail lines* (any order, all optional):
   - ~Saving Throws Str +5, Dex +3~
   - ~Skills Perception +5, Stealth +6~
   - ~Damage Vulnerabilities …~
   - ~Damage Resistances …~
   - ~Damage Immunities …~
   - ~Condition Immunities …~
   - ~Senses blindsight 60 ft., …, passive Perception N~
   - ~Languages Common, Draconic~
   - ~Challenge N (XP), proficiency bonus +N~
5. *Feature blocks* — anything before the next section header is
   a trait. Section headers we recognize: ~Actions~, ~Bonus
   Actions~, ~Reactions~, ~Legendary Actions~, ~Lair Actions~,
   ~Regional Effects~, ~Spellcasting~. Each section's content
   is split into individual features by their ~name.~ pattern
   (a phrase ending in a period at the start of a line).
6. *Spellcasting* sub-parses the slot lines (~"Cantrips
   (at will): …"~, ~"1st level (4 slots): …"~) into structured
   data.

** Implementation

#+begin_src elm :results none :exports code
type ParseError
    = MissingHeader
    | MalformedAbilityRow String
    | MalformedDetail { detail : String, raw : String }
    | UnrecognizedSection String

parseStatBlock : String -> Result ParseError CreatureDraft
parseStatBlock raw =
    raw
        |> String.lines
        |> List.map String.trim
        |> List.filter (not << String.isEmpty)
        |> walkSections
#+end_src

The walker maintains a small state record (~current section,
accumulated features~) and dispatches by line type.

** Live preview

The paste modal renders a live preview of the parsed creature as
the user types. Parse failures display the ~ParseError~ inline
("couldn't read Saving Throws line: 'Str+5, Dex+3'") so the user
can fix and re-paste without leaving the modal.

* Compendium → queue handoff

** UX flow

1. GM clicks *➕ Add Creature* in Encounter Controls.
2. Compendium browser modal opens.
3. GM searches / filters / picks a creature; the right pane shows
   the full stat block.
4. GM enters a count (default 1) and clicks *Add to Encounter*.
5. Modal closes; the queue gains N instances at their rolled
   initiative positions; the queue auto-sorts.

** Implementation

New Msg in ~Main.elm~:

#+begin_src elm :results none :exports code
| CompendiumAddToQueue String Int             -- (creatureId, count)
| CompendiumInitiativeRolled String Int (List ( String, Dice.Roll ))
                                              -- (creatureId, count, rolls)
#+end_src

Update branch dispatches a ~Dice.batchRollCmd~ over N specs (one
per copy), each with the creature's ~initiativeBonus~. The
~CompendiumInitiativeRolled~ handler walks the results, builds
N ~Encounter.Creature~ instances via ~Compendium.draftToInstance~,
auto-numbers their names against the current queue, appends them,
and runs ~Encounter.sortByInitiative~.

** Auto-numbering

#+begin_src elm :results none :exports code
uniqueInstanceName : String -> List String -> String
uniqueInstanceName base existing =
    let
        candidate i =
            if i == 1 then base else base ++ " " ++ String.fromInt i
        loop i =
            if List.member (candidate i) existing then loop (i + 1)
            else candidate i
    in
    loop 1
#+end_src

So adding three Goblins to a fresh encounter yields
~Goblin / Goblin 2 / Goblin 3~. Adding three more (with the
first three still alive) yields ~Goblin 4 / Goblin 5 /
Goblin 6~ — never collides.

** Edit modal (create / update)

Form sections follow the data model:
- Identity: name, kind (radio), size (dropdown), race, subrace,
  alignment, source.
- Combat core: AC + note, max HP + formula, initiative bonus,
  speed multi-input.
- Abilities: 6 number inputs in a grid; modifiers auto-derived
  and shown beneath each.
- Saves: dynamic add/remove rows.
- Skills: dynamic add/remove rows.
- Damage type lists: chip inputs.
- Senses: 5 number inputs + passive perception (auto-suggested
  from 10 + WIS).
- Languages: chip input.
- CR: text input + auto-suggest XP via standard table.
- Features: dynamic Trait / Action / Bonus Action / Reaction
  sections; each row has name + description textarea + optional
  usage selector.
- Legendary / Lair / Regional: collapsible advanced sections.
- Spellcasting: collapsible advanced section.
- Custom sections: dynamic rows.

Validation: ~name~, ~armorClass~, ~maxHp~ required on create.
Edit relaxes (mirrors old project).

** Paste modal

Single textarea + live preview pane. Pasting in the textarea runs
~Compendium.parseStatBlock~ on every change; the preview shows
either:
- The parsed stat block (if successful) with an *Apply to Form*
  button that hands the draft to the edit modal for final review,
  or
- A red ParseError detail with the offending line highlighted.

* Phased implementation plan

Each phase ships a buildable, testable slice.

** Phase 1 — Backend foundation

- Add ~uuid = "1"~ to ~crates/lib/Cargo.toml~.
- Define ~Creature~ + sub-types in
  ~crates/lib/src/compendium/types.rs~ with full serde derive.
- Drop bundled creatures JSON at
  ~crates/lib/data/bundled-creatures.json~ (start with 5
  hand-authored entries; expand later).
- Implement ~CompendiumStore~ with
  ~load_or_bootstrap / list / get / insert / update / remove /
  replace_all / reset_to_bundled~.
- HTTP routes in ~crates/server/src/compendium.rs~; merged into
  ~web_base.rs~.
- Add ~--compendium-path~ config flag; default
  ~<data_dir>/compendium/creatures.json~.
- Tests: round-trip JSON serde, atomic-write isolation,
  duplicate-id rejection.

** Phase 2 — Frontend domain layer

- Create ~frontend/src/Compendium.elm~ with the type definitions
  and JSON encoders / decoders matching the backend's serde
  shape.
- Add ~Db~ wrapper, ~search / filterByKind / sortBy*~ helpers.
- Add ~Compendium.draftToInstance~ and require a small
  ~Encounter.Creature.creatureId : Maybe String~ field
  addition. Update existing seeds + ~duplicateCreature~ to
  preserve / propagate the field.
- Wire HTTP fetch on app boot:
  ~Http.get { url = "/api/compendium/creatures", … }~ →
  ~CompendiumLoaded (Result Http.Error (List Creature))~.

** Phase 3 — Browser modal (read-only)

- ~CompendiumUi~ state in ~Model~.
- ~CompendiumOpen / Close / SearchChanged / KindToggled /
  SortChanged / CrRangeChanged / Selected~ Msgs.
- View: two-column layout, left list + right pane, sticky
  filter bar, action bar in right pane.
- ~viewStatBlock : Compendium.Creature -> Html Msg~ — the
  shared renderer used here AND in Quick View on cards.
- Compendium panel in the left sidebar gets a "Open" button
  that fires ~CompendiumOpen~.
- "➕ Add Creature" button in Encounter Controls also opens the
  modal (same handler).

** Phase 4 — Add-to-encounter handoff

- ~CompendiumAddToQueue id count~ Msg + handler.
- Auto-roll initiative via ~Dice.batchRollCmd~.
- ~CompendiumInitiativeRolled~ handler builds N
  ~Encounter.Creature~ instances, auto-numbers names, appends to
  queue, runs ~Encounter.sortByInitiative~, closes modal.
- "Add to Encounter" button in the modal's right action bar
  with count input (default 1, capped at e.g. 20).

** Phase 5 — Edit / create modal

- New ~CompendiumEditUi~ state (separate from browser ~Ui~).
- Form sections wired to all fields.
- Validation logic.
- ~POST~ on create, ~PUT~ on edit; on success refetch list and
  re-select the new creature.

** Phase 6 — Stat-block parser

- ~Compendium.parseStatBlock~ + ~ParseError~ type.
- Test corpus: ship a fixture file with 6+ varied stat-block
  pastes (Goblin, Bandit Captain, Ancient Dragon, NPC humanoid,
  spellcaster, lair-action monster) and assert each parses to
  the expected draft.
- Paste modal (~CompendiumPasteUi~ state) with live preview +
  *Apply to Form* button that hands off to the edit modal.

** Phase 7 — Quick View on cards

- ~Encounter.Creature.creatureId~ already added in Phase 2.
- Card right rail (or a row 3 button) gets a *🔍* button. On
  click, dispatches ~CompendiumQuickView creatureId~ which
  renders the stat block in a read-only modal.
- Disabled with tooltip when ~creatureId == Nothing~.

** Phase 8 — Import / export / reset

- *Export*: one button → ~window.location = "/api/compendium/export"~.
  Browser handles the JSON download via
  ~Content-Disposition~ on the response.
- *Import*: file picker (~<input type="file">~) reads the
  selected JSON via the file API, ~POST~ s the parsed list to
  ~/api/compendium/import~. Confirmation prompt warning that
  the existing collection will be replaced.
- *Reset to Bundled*: button with confirmation; ~POST~ s to
  ~/api/compendium/reset~ and refetches.
- *Single-creature export*: button on the right pane fetches
  the creature and triggers a single-record JSON download.

** Phase 9 — Polish

- Empty-state UX: "No creatures yet. Try importing or pasting a
  stat block."
- Loading skeletons on initial fetch.
- Toast notifications on success/failure.
- Keyboard navigation: ~/~ focuses the search box, ~Esc~ closes
  the modal, arrow keys move list selection, ~Enter~ adds the
  selected creature to the queue.
